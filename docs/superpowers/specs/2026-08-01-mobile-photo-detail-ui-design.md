# Mobile Photo Detail — Native Chrome Rebuild — Design

**Date:** 2026-08-01
**Scope:** Replace the hand-drawn chrome on the photo detail page with real system bars, add Photos-style immersive mode, rebuild the info inspector on a native `List`, bump the app to iOS 26 and strip every backwards-compat branch in `apps/mobile`.
**Touches:** `apps/mobile/modules/photo-masonry/ios/**`, `apps/mobile/modules/photo-masonry/index.ts`, `apps/mobile/src/modules/photo-viewer/**`, `apps/mobile/app.json`, `apps/mobile/package.json`, `PhotoMasonry.podspec`, `locales/mobile/en.json`.
**Supersedes:** the uncommitted chrome currently in the working tree (`PhotoDetailView.swift`, `PhotoDetailGlassSurface.swift`, `PhotoDetailSoftEdgeView.swift`, `PhotoDetailReactionRailView.swift`, the compact half of `PhotoInfoSheetView.swift`).

## Problem

The current detail chrome approximates Apple Photos by hand and misses on every axis that makes a control read as native:

1. `PhotoDetailGlassSurface` sets `UIGlassEffect.isInteractive = true` while hosting the button in `contentView` — the documented gotcha in root `CLAUDE.md`; the glass swallows touches meant for the button.
2. Four independent glass circles with no `UIGlassContainerEffect` host get no refraction and no adjacency merge; on a black backdrop they degrade to flat grey discs.
3. Toolbar glyphs mix enclosed and bare symbol families (`info.circle` next to `bubble.left`, `face.smiling`) at hand-picked point sizes (24/24/22/22), so their optical weights do not match.
4. The footer is two disconnected surfaces — a lone share circle plus a three-cell pill — of unequal visual weight.
5. Count badges are hand-rolled `UILabel` + `cornerRadius` at `ofSize: 9`, tinted `.systemBlue`; every system count badge (app icon, tab bar) is `.systemRed` at Dynamic-Type-aware metrics.
6. The nav subtitle crams `date, time · 5 / 6` onto one line. Photos never puts a page index in the bar.
7. `PhotoDetailView.swift` is 681 lines and lays out twelve views from one `layoutChrome` method — over the project's 500-line ceiling, and the direct cause of the metric drift above.

Hand-transcribing HIG metrics does not get more accurate on a second attempt. The fix is to stop transcribing them.

## Decisions (confirmed)

| Decision | Choice |
|---|---|
| Visual north star | Pixel parity with the iOS 26 Apple Photos detail view |
| Chrome construction | Standalone `UINavigationBar` + `UIToolbar` as plain subviews — no `UINavigationController` |
| Social actions | Bottom toolbar, four evenly-spaced items: share / info / comments / reactions |
| Nav bar copy | `title` = day line, `subtitle` = time (· place). The photo title appears only in the info panel |
| `···` more menu | Removed — it only duplicated share and info |
| Page position | ~~`UIPageControl` above the toolbar~~ — **superseded 2026-08-02: no position indicator at all** |
| Immersive mode | Single tap toggles; zoom force-hides; native owns status bar and home indicator |
| Active state | Symbol swaps to its `.fill` variant — never a blue tint |
| Comment badge | `.systemRed`, `.caption2` monospaced digits |
| Reaction rail | `UIGlassContainerEffect` hosting one `UIGlassEffect` per emoji, anchored above the fourth toolbar slot |
| Info panel | Native `List(.insetGrouped)` sharing section rendering with the existing sheet |
| Deployment target | iOS 26.0; every `#available` branch below it deleted repo-wide in `apps/mobile` |
| Out of scope | Thumbnail filmstrip scrubber, edit/adjust actions, iPad redesign beyond the existing side inspector |

## Phase 0 — Deployment target bump (must land first)

`apps/mobile/ios/` is gitignored and regenerated by prebuild, so `ios/Podfile` cannot be edited directly. The target must come from a config plugin, and `expo-build-properties` is not currently installed.

1. `pnpm --filter mobile add expo-build-properties`
2. `app.json` → `expo.plugins` gains:
   ```json
   ["expo-build-properties", { "ios": { "deploymentTarget": "26.0" } }]
   ```
3. `modules/photo-masonry/ios/PhotoMasonry.podspec`: `s.platforms = { ios: '26.0' }`
4. Full `npx expo prebuild --clean -p ios` followed by a simulator build.

**This is a spike, not a formality.** Expo SDK 57 makes no guarantee about 26.0 as a deployment target. CocoaPods will warn about third-party podspecs declaring lower platforms (benign); the real risk is a pod touching an API removed in 26. If the build breaks, it gets resolved before any UI work starts.

Accepted consequence: iOS 26 requires iPhone 11 or later. Existing TestFlight testers on older hardware stop receiving builds.

## Phase 2 — File decomposition

| File | Responsibility | Target |
|---|---|---|
| `PhotoDetailView.swift` | ExpoView shell: prop entry, event exit, child orchestration | ~220 lines |
| `PhotoDetailNavigationBar.swift` | Standalone `UINavigationBar`: transparent appearance, title/subtitle, back item | ~120 lines |
| `PhotoDetailToolbar.swift` | Standalone `UIToolbar`: four bar items, comment badge, active states | ~150 lines |
| `PhotoDetailChromeVisibility.swift` | Pure visibility state machine — no UIKit views touched | ~90 lines |
| `PhotoDetailInspectorPresenter.swift` | Pan-driven inspector displacement (compact + side layouts) | ~180 lines |
| `PhotoDetailReactionRailView.swift` | Reaction capsule on `UIGlassContainerEffect` | ~130 lines |
| `PhotoDetailScrimView.swift` | Single `CAGradientLayer` scrim, top and bottom | ~50 lines |

Deleted: `PhotoDetailGlassSurface.swift`, `PhotoDetailSoftEdgeView.swift`.

`PhotoDetailSoftEdgeView` layered a blur *and* a tint gradient at both edges; over a letterboxed black backdrop that only produced a grey band. It is replaced by `PhotoDetailScrimView`, a plain gradient with no blur, which exists solely for the case that actually needs it: a tall portrait photo that fills the viewport and runs under the bars. Starting value black α 0.38 → clear over 96pt, calibrated against Photos on the simulator.

`PhotoDetailView` instantiates the old class three times — a status-bar edge, a footer edge, and `detailTopSoftEdge` riding the inspector's upper boundary. Only the first two become scrims. The third is dropped outright: with the inspector rebuilt on an opaque `.systemGroupedBackground` list, a blur above its top edge is pure decoration.

## Nav bar

Standalone `UINavigationBar` pinned to the top; height from `sizeThatFits` plus safe area, never hand-computed.

```swift
let appearance = UINavigationBarAppearance()
appearance.configureWithTransparentBackground()
appearance.shadowColor = nil
appearance.titleTextAttributes = [.foregroundColor: UIColor.white]
appearance.subtitleTextAttributes = [.foregroundColor: UIColor.white.withAlphaComponent(0.6)]
bar.standardAppearance = appearance
bar.scrollEdgeAppearance = appearance
bar.overrideUserInterfaceStyle = .dark
```

One `UINavigationItem`:

| Slot | Content |
|---|---|
| `title` | Day line — `Today` / `Yesterday` / `Jan 12, 2024` |
| `subtitle` | `9:31 AM`, or `9:31 AM · Whistler` when a place is known |

**Superseded 2026-08-02.** Both lines now render through a custom `titleView`
(`PhotoDetailTitleCapsule`) rather than `navigationItem.title` / `.subtitle`.
Calibration found the system title illegible over bright photos with no opacity that
fixes it — the scrim is shaped backwards for this case, attenuating 20% at the screen
edge but only 4.8% at the subtitle. A glass title capsule solves it. This is a
deliberate, user-approved departure from the "let the system supply the title"
principle, and it costs the iOS 26 `subtitle` API that partly motivated the
standalone-system-bars route. The scrim survives at alpha 0.18 rather than 0.38.
| `leftBarButtonItem` | `UIBarButtonItem(image: UIImage(systemName: "chevron.backward"))`, `accessibilityLabel = strings.close` |
| right | empty |

No font or size overrides, and no `UIImage.SymbolConfiguration` on the back item — the bar supplies its own metrics. That is the entire point of the rewrite.

`overrideUserInterfaceStyle = .dark` is required because the backdrop is always black; without it the glass resolves for the ambient trait and washes out.

## Toolbar

Standalone `UIToolbar`, transparent appearance, `overrideUserInterfaceStyle = .dark`, items separated by `.flexibleSpace`:

| Item | Symbol | Active variant |
|---|---|---|
| Share | `square.and.arrow.up` | — |
| Info | `info.circle` | `info.circle.fill` |
| Comments | `bubble.left` | — (opens a page, no resident state) |
| Reactions | `face.smiling` | `face.smiling.fill` |

`UIBarButtonItem(image:)` is constructed without a symbol configuration so all four share the bar's metrics.

Active state swaps the symbol to its `.fill` variant. The existing `setButtonColor(..., .systemBlue)` path is deleted — tinting a toolbar glyph blue is a web idiom; Photos communicates state by filling the glyph (hollow heart → filled heart).

Comments and reactions are hidden when `socialActionsEnabled` is false, leaving share and info; `.flexibleSpace` re-distributes them automatically.

### Comment badge

`UIBarButtonItem` has no badge API, so the comments slot is a `UIBarButtonItem(customView:)` wrapping a `UIButton`, with a capsule `UILabel` pinned to its top-trailing corner:

- `backgroundColor = .systemRed`
- `font = UIFont.monospacedDigitSystemFont(ofSize: UIFont.preferredFont(forTextStyle: .caption2).pointSize, weight: .semibold)`
- minimum 16pt height, capsule corner radius, horizontal padding 5pt
- shown only when `socialActionsEnabled && commentCount > 0`; `99+` above 99
- `isAccessibilityElement = false`; the count reaches VoiceOver through the button's `accessibilityLabel`

## Reaction rail

```swift
let container = UIVisualEffectView(effect: UIGlassContainerEffect())
container.effect.spacing = 8
// one UIVisualEffectView(effect: UIGlassEffect(style: .regular)) per emoji,
// added to container.contentView; isInteractive stays false so the hosted
// button receives touches (root CLAUDE.md gotcha).
```

Presentation anchor moves from the bottom-right corner to directly above the fourth toolbar slot, horizontally centred on the reactions item. Count badges follow the comment badge metrics above.

Opening the rail closes the inspector; changing photo or opening the inspector closes the rail. Both behaviours already exist and carry over.

## Page control

`UIPageControl` centred above the toolbar, `numberOfPages = photos.count`, `currentPage` driven by `onNativeIndexChange`, `isUserInteractionEnabled = false`.

Hidden entirely when `photos.count > 20` or `photos.count <= 1`. A 500-photo gallery does not get a 500-dot strip; Photos solves that case with a thumbnail scrubber, which is out of scope.

## LIVE badge

`LivePhotoBadgeView` keeps its measured geometry — the comment block records that those numbers came from the real Photos badge. Only two changes: it joins the immersive fade, and its `UIBlurEffect(.systemUltraThinMaterialDark)` backdrop is compared against `UIGlassEffect(style: .clear)` on the simulator (open item below).

## Immersive mode

`PhotoDetailChromeVisibility` is a pure value type — three inputs, one derived output set, no view references. It is the only genuinely stateful part of this design, so it stays testable in isolation.

```swift
struct PhotoDetailChromeVisibility {
  var userHidden: Bool      // single tap toggle
  var infoProgress: CGFloat // inspector pan progress, 0…1
  var zoomed: Bool          // PhotoViewerCell.isZoomed
}
```

Derived:

| Output | Rule |
|---|---|
| `base` | `(userHidden \|\| zoomed) ? 0 : 1` |
| `navBarAlpha` | `base * (1 - infoProgress)` |
| `toolbarAlpha` | `base` |
| `pageControlAlpha` | `base * (1 - infoProgress)` |
| `topScrimAlpha` | `base * (1 - infoProgress)` — tracks the nav bar it sits behind |
| `bottomScrimAlpha` | `base` — tracks the toolbar |
| `liveBadgeAlpha` | `base` |
| `statusBarHidden` | `userHidden \|\| zoomed` |
| `homeIndicatorHidden` | `userHidden \|\| zoomed` |
| `allowsImmersiveToggle` | `infoProgress < 0.001` |

The nav bar fades as the inspector rises because the inspector's own header takes over that region. The toolbar stays because the inspector already reserves `bottomContentInset: 82` for it.

`userHidden` and `infoProgress > 0` cannot co-occur: `allowsImmersiveToggle` blocks the toggle while the inspector is up, and opening the inspector clears `userHidden`. `zoomed` and `infoProgress > 0` cannot co-occur either — `PhotoViewerView.allowsInfoGesture()` already refuses while zoomed.

### Status bar and home indicator

`PhotoViewerView` already resolves its `RNSScreen` via `findScreen()`. Native sets the traits directly:

```swift
screen.statusBarHidden = visibility.statusBarHidden
screen.homeIndicatorHidden = visibility.homeIndicatorHidden
screen.statusBarStyle = "light"
screen.statusBarAnimation = "fade"
```

`RNSScreen.mm:1263` and `:1283` guard those setters behind a prop diff, so React only clobbers them if JS changes the same props. Nothing in `apps/mobile/src/presentation` sets them, so native ownership is safe — but `<StatusBar style="light" />` must be removed from `PhotoDetailScreen.tsx`, otherwise expo-status-bar's global mechanism fights RNScreens' per-screen trait management. Style now comes from `screen.statusBarStyle`.

### Gestures

A new single-tap recogniser on `PhotoDetailView`. Three conflicts, all handled explicitly:

1. **vs double-tap zoom** — `PhotoViewerCell` promotes its double-tap recogniser to a stored property; `PhotoViewerView` gains `configureExternalTapGesture(_:)` (mirroring the existing `configureExternalInfoGesture(_:)`) which calls `tap.require(toFail: cell.doubleTapGestureRecognizer)` as cells are configured.
2. **vs chrome buttons and the LIVE badge** — `gestureRecognizer(_:shouldReceive:)` returns false when `touch.view` descends from the nav bar, toolbar, page control, reaction rail, or LIVE badge.
3. **vs the inspector pan** — no interaction needed; one is a tap, the other a pan.

### Animation

0.25s `UIView.animate` with `[.beginFromCurrentState, .allowUserInteraction, .curveEaseInOut]`, alpha only — no translation. When `UIAccessibility.isReduceMotionEnabled`, values are applied directly.

## Info panel

`PhotoInfoSheetView.swift` currently carries two renderings of the same data: a sheet built on `List(.insetGrouped)` and a compact inspector built from `LazyVStack` plus `RoundedRectangle` cards.

Extract the section body into a shared `PhotoInfoSectionsList` view used by both. The sheet passes its header; the inspector passes `showsHeader: false` and its bottom inset. `PhotoInfoInspectorView(info:showsHeader:bottomContentInset:onClose:)` keeps its current signature — only its internals change.

Deleted: `PhotoInfoCompactView`, `PhotoInfoCompactSectionHeader`, `PhotoInfoCompactRowsCard`, `PhotoInfoCompactParametersCard`, `PhotoInfoCompactTagsCard`, `PhotoInfoCompactToneCard`.

The "only allow pull-to-dismiss when the list is scrolled to the top" logic in `PhotoDetailView.gestureRecognizerShouldBegin` walks the hit-test chain looking for a `UIScrollView`; `List` is backed by one, so it carries over unchanged into `PhotoDetailInspectorPresenter`.

## JS changes

### `photoHeaderModel.ts`

`buildPhotoHeaderModel(photo, locale, fallbackTitle, now)` — the `currentIndex` and `total` parameters are dropped along with the page suffix. `HeaderPhoto` widens to `Pick<GalleryPhoto, 'city' | 'dateTaken' | 'location' | 'title'>`.

- `title` — the day line: `Today` / `Yesterday` for ±1 day, otherwise `dateStyle: 'medium'`. With no valid `dateTaken`, falls back to `photo.title.trim() || fallbackTitle`.
- `subtitle` — `[time, place].filter(Boolean).join(' · ')`. `place` resolves in strict order: `photo.location?.city`, then `photo.city`, then `photo.location?.country`, then none — country appears only when neither city field is set. Empty when there is no valid date and no place.

Existing `Intl` formatter caches are reused as-is.

### `PhotoDetailScreen.tsx`

- Remove `<StatusBar style="light" />` and its `expo-status-bar` import.
- Drop `more` from the `stringsJSON` payload.
- `buildPhotoHeaderModel` call sites lose the index/total arguments.

`photos.count` is already available natively, so the page control needs no new prop.

### `modules/photo-masonry/index.ts`

Remove `more` from `PhotoDetailStrings`.

### i18n

Delete `"photo.more"` from `locales/mobile/en.json`; ESLint strips the other locales automatically. It has exactly one call site (`PhotoDetailScreen.tsx:81`), which is going away.

## Open items — settle on the simulator, not from headers

These cannot be resolved from the SDK and are calibrated during implementation against side-by-side Photos screenshots:

1. Whether `.flexibleSpace`-separated toolbar items on iOS 26 render as **one shared glass capsule** or **four independent glass circles**. This determines the footer's silhouette. If Photos shows one capsule and `.flexibleSpace` breaks the group, switch to `.fixedSpace` with computed widths, or drive it via `UIBarButtonItem.sharesBackground`.
2. Whether a `customView` bar item (the comment badge) participates in the shared glass background at all. If it does not, all four items become `customView` so they stay visually consistent.
3. `PhotoDetailScrimView` opacity — 0.38 is a starting point, verified against a full-bleed portrait photo.
4. `LivePhotoBadgeView` backdrop: keep `UIBlurEffect(.systemUltraThinMaterialDark)` or move to `UIGlassEffect(style: .clear)`.
